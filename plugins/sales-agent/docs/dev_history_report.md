## 問題点の詳細

### 1. 追加→削除の往復: 連絡先カバレッジ確認ステップ

- `2f67fc9`（#11）: build-list に「ステップ7: 連絡先カバレッジの確認」を追加。登録済み営業先のメール/フォーム率が80%未満なら公式サイト再訪問で補完する仕組み。
- `b4e1f74`（#7）: build-list を2フェーズ構成にリファクタした際に、このステップを丸ごと削除。Phase 2（enrich-contacts サブエージェント）が連絡先取得を担うため不要になった。

**評価:** 設計変更に伴う自然な消滅ではあるが、#11の時点でこのステップを追加した判断が早計だった。2フェーズ分離が視野に入っていれば不要だったはず。実害はないが、レビュー・コミットの往復コスト分は無駄。

### 2. 2段階のSQL移行

- `2f67fc9`（#11）: outbound の list-reachable クエリにチャネル優先順のORDER BYを追加。この時点ではまだ `query_db.py` にインラインSQLを渡す方式。
- `45aa572`（#5）: `sales_queries.py` を新設し、全スキルのインラインSQLを名前付きクエリに移行。#11で整備したORDER BYも含め、全SQLがスクリプト内に移動。

**評価:** #11で凝ったORDER BYを `query_db.py` のインライン引数として追加し、直後の#5でそれを `sales_queries.py` に移すのは二度手間。`sales_queries.py` の導入と同時にORDER BY改善を行えば1回で済んだ。ただし、#11と#5の間にはバージョンbump（#10）があるので、リリースサイクル上やむを得なかった可能性もある。

### 3. daily-cycle の evaluate 条件の重複定義

- `2f67fc9`（#11）: evaluate SKILL.md 内にデータ量ゲート（30件未満・3営業日未満はスキップ）を追加。
- `45aa572`（#5）: daily-cycle SKILL.md に `last-evaluation` クエリを追加し、「3営業日以上経過した場合のみ evaluate を起動」というゲートを追加。

**評価:** evaluate 内部のゲートと daily-cycle のゲートは異なる役割（evaluate内部は「データ量が足りるか」、daily-cycleは「前回から十分間が空いたか」）なので厳密には重複ではない。ただし「3営業日」という数値が両方に登場するため、一方を変更した場合にもう一方の更新を忘れるリスクがある。定数の一元管理が望ましいが、現状の規模では実害は小さい。
